4 common misconceptions

✗ Misconception

"The buzzer should only sound while screen 2 (air quality) is showing — otherwise it doesn't make sense."

✓ Reality

The buzzer check runs once per loop, before either screen displays — it's completely decoupled from what's currently on the LCD. A real alarm system should never depend on which screen a display happens to be showing; safety logic and display logic are deliberately kept separate.

✗ Misconception

"I should make a bigger LCD message that shows all three values on one screen using smaller text."

✓ Reality

Character LCDs cannot resize text — every character occupies a fixed 5×8 pixel cell. The only way to fit more information is either a bigger physical display (20×4) or, as this project does, cycling through multiple screens over time. Both are valid; cycling is far cheaper.

✗ Misconception

"Adding a buzzer alarm for temperature and humidity too would make the system more thorough."

✓ Reality

More alarms is not automatically better — too many trigger conditions cause alarm fatigue, where users start ignoring alerts entirely. This project deliberately limits the alarm to one critical condition (air quality), keeping it meaningful. Real systems carefully choose which conditions actually warrant an alert.

✗ Misconception

"Reusing readAirQuality() from the previous topic means I'm not really learning anything new."

✓ Reality

Reusing a well-tested function is exactly how real embedded engineers build larger systems — verified building blocks get assembled into bigger projects rather than rewritten from scratch each time. The new skill here is the screen-cycling architecture and decoupled alarm logic, not the sensor reading itself.
